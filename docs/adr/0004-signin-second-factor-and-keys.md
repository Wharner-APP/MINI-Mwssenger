# 0004. sign.in как обязательный второй фактор и иерархия ключей

## Контекст

Вход должен быть невозможен без файла даже при известном пароле, а сервер не должен получать ничего, из чего можно восстановить файл или ключи шифрования переписки.

## Решение

При регистрации клиент генерирует sign.in и выводит из него ключ файла, а из него — отдельные ветви для аутентификации, шифрования и целостности; из пароля отдельно выводится ключ пароля. На сервер внутри TLS уходят только ключ аутентификации и ключ пароля; сервер хранит их Argon2id-верификаторы и сравнивает за постоянное время.

## Почему

Рассматривали второй фактор через телефон или почту — запрещено условиями. Резервный код как основной фактор — его тоже можно потерять, и он отложен. Хранение файла на сервере — сервер получил бы доступ. Один пароль как носитель всех ключей — смена пароля ломала бы историю. Разделение ветвей позволяет менять пароль без перешифровки истории и перегенерировать файл с фоновой перешифровкой.

## Последствия

Потеря sign.in означает потерю доступа и локальной истории — это свойство модели, а не дефект. Перегенерация файла требует фоновой перешифровки базы с откатом при сбое. Ключ аутентификации и ключ пароля всё же покидают устройство внутри TLS, и это прямо записано в модели угроз. Формат файла и правила нормализации становятся контрактом: менять их можно только с миграцией всех пользователей.
